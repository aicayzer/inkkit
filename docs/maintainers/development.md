# Development

CI runs Node.js 26, and the package declares Node.js 26 or later (`engines` in `package.json`). Older Node.js versions are not supported. Use the package-manager version in `package.json`.

```sh
pnpm install --frozen-lockfile
pnpm exec playwright install chromium webkit
pnpm check
pnpm format:check
pnpm build:playground
pnpm test:built-playground
```

`pnpm test:built-playground` opens the built `_local/playground/index.html` as a file and checks that a diagram renders, so a build that has lost Pele fails. It guards the `./src/index.ts` entry in `sideEffects` in `package.json`, which stops the playground build from tree-shaking the Pele registration; the package does not ship `src`, so the entry has no effect on hosts. Build the playground first. CI runs it after the build.

`pnpm test:docs` checks the built declarations against owned descriptions in [`docs/reference/`](../reference/), including exports from both package entries, public editor members and fields of exported interfaces. It also runs negative checks proving that examples, incidental mentions and another type's same-named field cannot satisfy a missing description. Build first. [API reference validation](api-documentation.md) explains ownership annotations, nested fields and the check's limits.

`pnpm dev` starts the [development playground](playground.md); it does not start a browser automatically. `pnpm test:package` packs the built package, installs it in a fresh consumer with an isolated npm cache, checks declarations and CSS, and builds an offline single-file Vite page. It builds a second consumer from the `@aicayzer/inkkit/core` entry and checks that its page contains neither Pele nor DOMPurify code. It then opens both pages from a file URL in headless Chromium and WebKit. Each page fails on a page error, a network request, or a stylesheet that does not style the editor root, and fails unless `snapshot()` returns the loaded bytes exactly and a typed edit, undo and redo save the expected bytes. The archive and `package-evidence.json` are written to ignored `_local/release/<version>/`, preserving evidence from earlier releases. Evidence records the commit, working-tree state, compressed SHA-256, npm integrity, decompressed tar SHA-256, and the SHA-256 and size of both offline pages. Commit the candidate before recording final evidence; release verification rejects evidence from a dirty working tree.

`pnpm check` needs network access: its packed-consumer test installs the package and build tools into a clean consumer. The resulting pages run offline. `pnpm test:browser` runs the Chromium suite; use `pnpm exec playwright test --project=webkit` for WebKit and `pnpm exec vitest run test/<name>.test.ts` for one unit file.

The public API is `src/core.ts`; `src/index.ts` registers Pele and re-exports it. App hosts own persistence, native menus and file access. Regression tests cover formatting, source preservation, clipboard import/export, tables, snapshots, asynchronous image/file operations and optional wiki links. The clean consumer compiles `FileAdapter`, `WikiLinkAdapter`, their reference/context/presentation types and `EditorOptions` alongside the existing public facade. CI uses hosted runners.

The [internal architecture](architecture.md) describes the editor facade and its collaborators.

## Dependencies

The package bundles its runtime dependencies into `dist`, so a host runs the exact code that Inkkit tested. Milkdown, ProseMirror, micromark, the mdast utilities, lowlight, Pele and DOMPurify are `devDependencies`, and the build bundles them with their own dependencies. `pnpm build` bundles the versions in `pnpm-lock.yaml`, the same tree that Vitest, the browser suite and the playground run. A host's lockfile cannot resolve a different parser, serializer or ProseMirror version for Inkkit.

Pele is pinned exactly and bundled behind the main-entry registration with DOMPurify. The core entry reaches neither library. Inkkit validates the parsed diagram model before rendering and sanitizes the resulting SVG. Rendering never changes saved bytes; hosts install no separate runtime dependency.

- `pnpm build` runs `tsc` for declarations only, then `vite build --config vite.package.config.ts` for the JavaScript, then `scripts/finish-build.mjs`. That script keeps only the declarations the public entries reach and fails if one of them imports a package, because hosts do not install the bundled packages.
- The build writes `dist/THIRD-PARTY-NOTICES.txt` with the name, version, license and notice texts of every bundled package. The generated file includes Pele's full license file, including its Lucide ISC notice. The build copies the same contents to `dist/THIRD-PARTY-NOTICES-FULL.txt` for compatibility with existing host recipes. Both files are regenerated by every build, including release CI. [The host recipe](../guides/web-view.mdx#carry-the-license-notices) explains why hosts must generate their own notices as well.
- To update a bundled package, change `pnpm-lock.yaml` in a pull request. CI then runs the preservation tests in `pnpm check`, the packed-consumer pages and the whole browser suite against the new tree before it can merge.

The pinned `prosemirror-view@1.42.6` patch in `patches/` cancels deferred focus restoration when a key that can edit or move the caret arrives. Otherwise, the focus timer can restore an old caret before the browser delivers `selectionchange`. Before handling a non-modifier key, it also reads the current DOM selection even if no observer timer is pending, then retires the recent-focus safeguard. This keeps a deletion after a find-and-arrow movement at the browser's caret while preserving focus correction during the first arrow. Composition and Android input guards still run before this read. Pure modifier keys retain the normal focus correction; blur and destruction clear the pending timer. Keep the patch's source and both distributed JavaScript entries aligned. `test/focus-input.test.ts` controls that event ordering through the public facade and DOM; native host checks must also exercise real keyboard input. Reassess the patch when updating ProseMirror. The same patch uses binary search over sorted decoration-child offsets, avoiding a scan of preceding siblings for each item in a long task list. `test/task-decoration-lookup.test.ts` bounds child-offset reads while facade edits render, and checks exact save, undo, redo and reopen bytes.

The pinned `prosemirror-drop-indicator@0.1.4` patch resets the last pointer coordinates when a drag leaves or ends, so a later drag at the same point shows the indicator again, and cancels the pending hide timer on destruction. Keep its source and distributed JavaScript aligned when updating the dependency. `test/browser/drop-indicator-lifecycle.spec.ts` checks reentry, visibility, contrast and the color token; `test/drop-indicator.test.ts` checks timer cancellation.

The trade-off: a security fix in a bundled package reaches hosts only through an Inkkit release, and a host's dependency audit does not see bundled packages. Dependabot alerts are on for this repository and read `pnpm-lock.yaml`, so they cover the bundled packages. When an alert affects a bundled package, update it in a pull request and release.

## Bounded verification

Choose checks from the changed behaviour, not from every available fixture combination. The [CI policy](#ci-policy) says which checks hosted CI runs and when.

For a maintenance group, run focused checks while implementing each change, then run the complete browser and relevant native suites once on the combined final candidate before release. A later change requires the checks it affects; an identical source tree after rebasing does not require another run. Preserve the earlier commit and tree identity with the evidence. Hosted CI still runs its normal checks on each pull request and merge.

Randomized tests use independent, deterministic samples: `SOURCE_TYPING_SEEDS=60`, `PRESERVATION_LIST_SEEDS=400`, `PRESERVATION_LOCAL_SEEDS=600`, `PRESERVATION_STRUCTURAL_SEEDS=300` and `RICH_TEXT_CONVERT_SEEDS=300`. Set only the relevant variable to increase a run, for example `SOURCE_TYPING_SEEDS=200 pnpm exec vitest run test/source-typing.test.ts`. Source typing compares the formatted document's structure and marks, not only its readable text.

The browser suite includes the bounded long-note scaling check. Run it alone with `pnpm exec playwright test --project=chromium test/browser/long-note-scaling.spec.ts`; [performance](performance.md) defines its documents, measurements and allowance.

| Trigger                                                                                 | Required evidence                                                                                                                                                                 |
| --------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Final code or package candidate                                                         | `pnpm check`, `pnpm format:check`, `pnpm build:playground`, `pnpm test:built-playground`, actual packed-consumer verification and the whole browser suite in Chromium and WebKit. |
| Changed editor behaviour                                                                | Focused regression tests and selected browser cases for the changed contract, including failure and untidy input.                                                                 |
| Changed WKWebView, focus/input, bridge, clipboard, print or resource lifecycle boundary | Selected native core plus relevant feature cases from the existing WKWebView runner, using the actual candidate archive.                                                          |
| Changed Swift package or RTF fixtures                                                   | `swift test` on macOS 27 with Xcode 27.                                                                                                                                           |
| Source-only documentation change                                                        | Review changed facts and examples; no editor or native run. Mintlify page, asset or configuration changes validate the site.                                                      |
| Publication                                                                             | Clean committed candidate evidence, exact registry-version consumer and archive/integrity comparison under [releases](releasing.md).                                              |

Unit integration tests mount `InkKitEditor` and assert saved bytes through `snapshot()`. The test-only helpers in `test/editor-access.ts` provide typed access to the Milkdown context and adapter options when a test must drive a transaction or control an adapter. Direct preservation tests retain independent algorithm and fast-path comparisons; accepted randomized local, region, list and correspondence edits also save and reopen through the public facade. Correspondence seeds and individual region edit steps are reported as separate cases with the normal test timeout. Region steps share one lazy traversal per seed, including attempts that produce no edit or fall back to whole-document validation. Their suites share editor assembly, then load each source through the facade to reset document state. The complete runs also check aggregate coverage; selecting one seed or step does not claim that aggregate coverage. Expanded case counts include those existing seeds and steps, not additional coverage.

Browser tests use the public facade and normal DOM interaction. Use [Playwright's standard CLI](https://playwright.dev/docs/test-cli) to list and select tests, inspect reports and open traces; see the [playground guide](playground.md). The fixture catalogue is selectable. Do not run its fixtures, configurations and adapters as a Cartesian matrix. Before pushing, run the affected Chromium specs, and the WebKit specs when selection, input, clipboard or layout changes; CI runs both engines on every pull request that changes the editor. A test that cannot run in an engine calls `test.skip` with the reason, for example because it uses the Chrome DevTools Protocol or a macOS key binding. Fix a flaky test at its cause; CI does not retry. Local results do not establish that hosted CI passed.

CI installs browsers with `node scripts/install-browsers.mjs <engine>...`, which runs `playwright install --with-deps` with up to three attempts of five minutes each, because a stalled package mirror once hung the step for 30 minutes; each install step also has a 17-minute limit. After the first failed installation, it replaces an Azure archive or GitHub mirror-list source with Ubuntu's archive before retrying, leaving security sources unchanged. Failure to install that fallback fails the step. `--no-deps` skips apt setup and mirror changes. `node --test scripts/install-browsers.test.mjs` checks retries, timeouts, recovery ordering and the source replacement. A real successful hosted install is still required to establish runner availability. CI runs browser tests with `node scripts/test-browser.mjs --project=<engine> --shard=<N>/3`; the runner forwards its arguments to `playwright test`. The runner owns Vite and Playwright, waits up to 30 seconds for readiness, and terminates both process groups if the server exits during the run. Its error includes the server exit code or signal. Vite stdout, stderr and the exit diagnostic are saved in `_local/playwright/server.log`, which each shard uploads with its failure artifacts. Playwright's `webServer.timeout` bounds startup only, so the runner supervises the server for the whole run. Direct `pnpm exec playwright test` commands continue to use Playwright's server management. Run `node --test scripts/test-browser.test.mjs` to check crash handling and normal completion.

Node/V8 fatal headers (`abort:` or `FATAL ERROR:`) on Vite's stderr also fail the browser run immediately. A fatal runtime error can stop the server from responding before its process exits. The runner retains the received diagnostic and stops both process groups; it does not retry the tests.

CI browser shards build the common fixture once, then serve its static output to each isolated test context. This reduces repeated module loading without sharing editor state. The browser fixture has two explicit modes for controlled comparisons. Set `INKKIT_BROWSER_FIXTURE=dev` to serve the fixture's source modules or `INKKIT_BROWSER_FIXTURE=built` to build and preview it. Both `node scripts/test-browser.mjs ...` and direct Playwright commands accept the variable. Without it, local commands retain the ordinary development playground. Set `INKKIT_BROWSER_FIXTURE=built` when reproducing a CI shard or running the final complete browser suites. Built mode rebuilds `_local/browser-fixture` before serving, uses unminified production output with source maps, and retains the 30-second startup bound. The playground and test-only core and preservation entries share one module graph, so prototype fault injection reaches the actual editor. In built mode, exact legacy source imports re-export the corresponding built entry and unknown source imports fail. This fixture does not replace the offline built-playground, packed-consumer or native checks.

The [existing native runner](../../scripts/interop/README.md) preserves earlier scenarios and supports `--list`, `--group` and `--scenario` selection. Run a bounded core and the cases matching a changed native boundary. Retain its summary and individual input/result JSON beside package evidence. A rejected or empty selection is a failure, not a zero-case pass. Record exact commands, reviewed commit, bundle/host hashes and failures. Preserve older release evidence.

Build and run using the [native runner recipe](../../scripts/interop/README.md#build-and-run). There is no fixture-version argument; evidence identifies the installed candidate and verifies its bundle hash. Default selection is the current bounded core. Select relevant additional groups for both development and releases, and run the core group against the core-entry consumer. An uncaught page error or unhandled rejection fails its scenario. `node --test scripts/interop/verify-native.test.mjs` checks selection, metadata, specialised result validation, history-clock restoration and failure-safe pasteboard handling without opening a window. The [selected native probe groups](../../scripts/interop/README.md#selected-native-probes) consolidate the keyboard/clipboard and image-drag regressions; select the relevant group and its documented host/helper requirements.

A native facade consumer establishes behaviour in WKWebView with its fixture bridge. Browser WebKit does not prove WKWebView behaviour, and neither proves a consumer app's native actions or compatibility with an external clipboard destination. Synthetic composition events test guards and transitions; they do not establish complete IME interoperability. Include those limits in the handover.

Run an external-app check only for a changed interoperability contract or a reproduced destination-specific bug. State the contract, application and transfer direction before testing one relevant case with disposable content. Reuse captured clipboard fixtures when an app is unnecessary. Do not routinely repeat Obsidian/Mail/consumer-app combinations or resume the unfinished 0.0.7 return matrix. Protect and restore the clipboard and affected preferences for native probes that use them; never use production notes or send mail.

Use `pnpm exec playwright test --config playwright.diagnostics.config.ts --project=chromium` to demonstrate browser failure reporting. It must exit non-zero with actionable diagnostics under `_local/playwright/controlled-failure/`. Native intentional-failure commands are in the [runner recipe](../../scripts/interop/README.md#fixture-operations). Keep expected failures separate from passing evidence. An unrun test is unverified.

App integrations and app releases follow package publication as a separate delivery phase. Temporary `file:` dependencies must not enter merged app lockfiles.

Documentation-only changes to Markdown guides, the README or agent instructions run a formatting check and skip editor tests. Mintlify pages, assets and configuration run `mint validate`. Unknown file types, mixed changes and release runs retain the full checks. The workflow still starts for every pull request so required checks resolve; it skips expensive steps rather than filtering out the workflow.

## Swift package

`InkKitRTF` is a Swift package for reading and writing RTF. `Package.swift` is at the repository root, the sources are in `apple/Sources/InkKitRTF` and the tests are in `apple/Tests/InkKitRTFTests`. The tests share fixtures with the editor in `test/formats/rtf/fixtures/`.

The package has no version of its own. It is versioned and tagged with the npm package: SwiftPM resolves the `v<version>` tag that the release creates. The `files` allowlist in `package.json` keeps `Package.swift` and `apple/` out of the npm package.

The package targets macOS 27 and iOS 27. To test it, use a macOS 27 machine with Xcode 27:

```sh
swift test
```

Golden fixture JSON records the expected parse of each RTF fixture. Regenerate it only with `INKKIT_RTF_UPDATE_GOLDEN=1 swift test`, then review every changed file before you commit. A regenerated golden file that nobody reviewed hides a regression.

CI runs `swift test --parallel` in the `swift` job on the `xcode-27` runner. The job runs when a change touches `Package.swift`, `apple/`, `test/formats/rtf/fixtures/` or `ci.yml`, and a release always runs it.

## GitHub workflow

The [Inkkit Project](https://github.com/users/aicayzer/projects/3) is the working roadmap. Issues describe outcomes and acceptance criteria; milestones group releases. [GitHub releases](https://github.com/aicayzer/inkkit/releases) record published versions and their verification evidence. Permanent client-app adoption remains separate work. Use feature-first Project views to track implementation, and version milestones to group delivery scope and publication status.

- **Roadmap** lists open feature issues, excluding release records, ideas and cancelled work.
- **Upcoming** groups the scheduled version milestones.
- **Delivery** shows Ready, In progress and Review work.
- **Feature board** shows feature status; **Ideas** and **Cancelled** retain separate decisions.

Use the version milestone to read scope and the publication checklist. These views are navigation aids; live issue acceptance criteria and milestone records remain authoritative. Keep implementation decisions with their issue rather than duplicating the backlog in documents.

- **Backlog:** scoped work awaiting readiness or dependencies.
- **Ready:** agreed and sufficiently scoped. This does not start an agent session.
- **In progress:** an authorised session is implementing the issue.
- **Review:** a reviewable result awaits acceptance or merge.
- **Done:** accepted implementation has merged, or a release has been published and verified.
- **Cancelled:** work will not proceed. Record the reason and close as **not planned**.

A delivery session names its issue or milestone and stopping point. Read the current issue, dependencies and relevant contracts; choose the implementation and delegate useful independent work. An issue being Ready is not publication authority.

Add new work to the Project. Keep unapproved ideas unscheduled with the `idea` label; remove it when scope is accepted. Link pull requests to their implementation issues and include relevant verification and remaining limitations. Use closing references for completed implementation. Keep future publication checklists and their results in milestone descriptions and release evidence; do not create new version-shaped release issues.

Main requires pull requests with passing CI and resolved review conversations. Use squash merges; merged remote branches are deleted automatically.

When stopping with work outstanding, leave a short issue update with the current state, decisions and next action. Update status when it changes; avoid routine progress narration. Close completed issues as **completed** and set **Done**. Generic closed-to-Done and automatic issue-closing workflows are disabled so cancellation and publication gates remain explicit.

Existing historical release issues retain their records. For future versions, complete the milestone publication checklist only after npm version, integrity and clean-consumer installation are verified. Review status or an open milestone does not authorise publication. App adoption and app releases are separate work. Follow [the publication procedure](releasing.md) before pushing a version tag.

Repository prose follows the Google developer documentation style guide. Keep issues, pull requests and comments concise; code comments explain reasons or constraints that the code cannot express.

## CI policy

The CI workflow (`.github/workflows/ci.yml`) runs on pull requests and, through the release workflow, on a release tag. It does not run on pushes to `main`. Branch protection requires pull requests to be up to date and takes only squash merges, so the merged tree is the tree that passed. A new push to a pull request cancels its running checks; a release run is never cancelled.

**Lanes.** The `changes` job runs `scripts/ci-scope.mjs` on the files a pull request changes and sets one flag for each lane. A tag, a release call or a missing history sets all of them. `scripts/ci-scope.test.mjs` is the specification of the rules.

| Lane         | Runs when the pull request changes                                                                                                      | Jobs                                                                                   |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| `editor`     | Anything except prose (`README.md`, `AGENTS.md`, `CLAUDE.md`, `docs/**/*.md`) and the documentation site (`.mdx`, images, `docs.json`). | `check`, `unit` (3 shards), `browser-chromium` (3 shards), `browser-webkit` (3 shards) |
| `site`       | The documentation site files under `docs/`.                                                                                             | `docs` (`mint validate`)                                                               |
| `swift`      | `Package.swift`, `apple/`, the shared RTF fixtures or the workflow.                                                                     | `swift` (`swift test` on macOS 27)                                                     |
| `playground` | `playground/`, `docs/snippets/`, `src/style.css`, themes, the demo and playground specs, build and test configuration or the workflow.  | `browser-playground` (the playground and docs demo specs in Chromium)                  |

A change to prose only runs the formatting check in `check`. A draft pull request skips the browser lanes; marking it ready starts a new run that includes them. A skipped lane counts as a pass.

**What each editor job covers.**

- **`check`** runs formatting, the script tests, typecheck, the package build, the API reference check, the packed-consumer test and the built-playground check. The packed consumer opens its pages in Chromium on pull requests and in Chromium and WebKit on a release. On a release it also uploads the packed `package-candidate` archive that the publish job releases.
- **`unit`** runs Vitest in three shards. `test/shard-sequencer.ts` deals test files out in name order, so the slow `preservation-*` suites land in different jobs.
- **`browser-chromium` and `browser-webkit`** run the whole browser suite in three shards each, against the built fixture, on every pull request that changes the editor. WebKit runs on GitHub-hosted macOS, because the host apps ship on WebKit. A job's shard name is `browser-<engine> (N/3)`, and it uploads its Playwright report and traces for seven days only when it fails.

**The required check.** The `CI result` job depends on every other job. It passes when each one succeeded or was skipped, and fails when one failed, was cancelled or never got a classification, so a skipped lane never leaves a required check pending. The `main` ruleset requires `CI result` alone, with branches up to date; add a new job to its `needs` list when you add a lane.

**Not in the default suites.** These run on demand, and no workflow runs them:

- `pnpm measure:browser` runs `scripts/measure-browser/`, which records timings and asserts nothing. Use it for the measurements that [performance](performance.md) describes.
- `pnpm test:playground` runs the playground and docs demo specs locally. CI runs them only in the `playground` lane.
- `pnpm exec playwright test --config playwright.diagnostics.config.ts --project=chromium` demonstrates failure reporting, as described under [bounded verification](#bounded-verification).

**Changing CI.** A new lane needs a rule in `scripts/ci-scope.mjs`, a case in its test, a job guarded by the lane's flag and an entry in the `needs` list of `ci-result`. Pin each action to a commit, run on GitHub-hosted runners only, and keep the release workflow calling this file so that a release runs every lane.
