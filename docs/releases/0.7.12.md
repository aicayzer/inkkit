# Inkkit 0.7.12

This patch release stops saving the space at the end of a typed paragraph. It changes no public API.

**Spaces at the end of an edited block aren't saved.** Predictive text on a phone ends almost every typed sentence with a space, and Inkkit wrote that space as `&#x20;`, which other Markdown apps show as text. Now, in a paragraph, heading, list item or table cell that an edit reaches, the spaces and tabs after the last text are left out of `snapshot()`. Typing `Milk and bread. ` saves `Milk and bread.`.

- The editor keeps the space and the caret after it, so the next word you type follows it. The space is gone when the saved text is opened again.
- A space that changes nothing else, such as one typed at the end of an unedited paragraph, leaves the text as loaded: the revision increases, `changed` doesn't fire and `dirty` stays `false`.
- An unedited document still saves byte for byte. A block that an edit doesn't reach keeps its bytes, including a `&#x20;` at its end, and so does a block that reads exactly as a loaded block, such as one that Undo restores.
- Spaces at the start of a block and beside a soft line break are still written as `&#x20;`. Hard breaks keep their spelling, and spaces before or after a pending break at the end of a paragraph are left out with it. Code blocks, inline code and literal Markdown are unchanged. A block of only spaces keeps them, and a non-breaking space is kept.
- A space typed after a bare URL at the end of a block no longer turns the URL into `<https://example.com>&#x20;`; the URL stays bare.

See [preservation](https://inkkit.cyzr.me/concepts/preservation#when-a-block-is-written-afresh).

Hosts update the package and rebuild their offline page. A host that compares saved text with what the editor shows, or that expects a `changed` event for every keystroke, should allow for a final space that isn't saved. The unchanged `InkKitRTF` Swift package resolves from the same release tag.
